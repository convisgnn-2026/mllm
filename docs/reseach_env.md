llm-pilot의 레버였던 Offloading 전략은 우리 상황에서 DiT, LLM, VLM의 PD분할, KV cache offloading (not AO), EPD 등 이기종 기법으로 활용. 

IB와 여타 환경 제약으로 인하여, 이기종 관련 서빙 최적화 실험은 현재 서버의 이기종 GPU로 할 예정임. 
대규모 (B300, Pro 6000) 환경은 옵션으로 두고 필요 시 활용 가능함.

따라서, 우리는 고정된 온프레미스 GPU 환경에서 DiT, VLM, LLM 워크로드가 실시간으로 주어질때 SLO를 만족하면서 비용효율성이 최대화 되는 Solver를 개발하는것이 목적. 

Solver는 Router 아래서 작동하며, Input으로 SOlver에게 작업이 들어오면, solver가 워크로드에 맞는 서빙 전략을 수학적으로 모델링하고 우리가 보유한 클러스터에서 (현재 가용 가능한) 가장 효율적인 자원 할당을 해주는것이 목표.

시뮬레이션으로 구성 할 예정임. 

이전 폐쇠망에서 만들던 mllm (vidbench)의 cosolve.py위주로 구현된 코드들은 참고만하고 새로운 solver인 hetsim을 만들려고 함.

# 조율 기록 (확정된 것만 위에서 아래로 추가)

## 확정 (2026-09-21)

1. **입력 단위 = 개별 추론 요청.** 사내 AI 플랫폼 사용자의 추론 요청이 하나씩 들어온다.
   (예: LLM 코딩 요청 — 인풋 짧고 아웃풋 긺.) 서비스 배포 요청 단위가 아니다.
2. **Solver 의 출력 = 서빙 전략 + 자원량.** 현재 가용 자원 풀을 보고
   "PD 분할로 할지 / KV cache 오프로딩으로 할지 …" 를 판단하고,
   "GPU 몇 개 · CPU(호스트 자원) 얼마" 가 지금 풀에서 최선인지를 낸다.
3. **Router 의 역할 = 실행.** Solver 가 낸 결과대로 사용자의 작업에 자원 할당을 처리한다.
   (현업 베이스라인: router 하나 + round-robin.)
4. **레버를 부르는 말로 "절단(cut)" 은 쓰지 않는다.** LLM-Pilot 의 "오프로딩(KVO·AO)을 수학적으로
   모델링해 고르는 레버" 라는 관점을 멀티모달로 확장하는 방향으로 본다. (명칭·정식화는 논의 중)
5. **참고 구현물.** TetriServe 구현물의 벤치마크, LLMServingSim 시뮬레이터 (이전 세션에서 참고함).
6. **이 서버의 실측 GPU** = RTX 4090 24GB ×1 + RTX 3090 24GB ×1 (nvidia-smi 확인).

7. **AO(attention offloading)는 배제.** 공식은 있지만 AO 가 끼면 solver 가 난해해질 위험이 크다.
8. **SLO 는 TetriServe 의 아이디어를 참고.** (요청별 마감 = SLO Scale × 기준 지연, 지표는 SAR.)
   그들의 수치를 그대로 쓸 필요는 없고 우리 상황(LLM·VLM·DiT 혼합)에 맞게 바꾼다.
9. **Router 의 역할을 배치로만 제한하지 않는다.** Router 가 맡는 편이 좋은 역할이 있으면 맡긴다.
   (3번의 "실행" 은 최소 역할이지 상한이 아니다.)
10. **실험 순서.** ① 4090·3090 실측으로 이기종의 효용성(고정 온프레미스에서 처리량을 높일 수 있는지)을 확인
    → ② 수학적으로 모델링 → ③ 시뮬레이션에서 scale-up.
11. **동작 구조.** Solver 는 요청의 특징(모달리티, 입력 길이, 예상 출력 길이, SLO)을 보고 판단한다.
    맞는 구성의 인스턴스가 이미 떠 있으면 거기에 태우고, 없거나 부족하면 가용 자원에서 새 구성을 띄우되
    기동 비용(워커 cold start 실측 33초)을 모델에 넣는다. 요청마다 새로 띄우는 배치 작업형이 아니다.
12. **회사 요구의 범위.** 회사의 요구는 "단순한 router 를 smart 하게" 뿐이다. 무엇을 어떻게 할지는
    우리가 계획해 실험하고, 효과적임을 밝히면 된다.

13. **이기종 효용성 실측의 비교 구성 (4090 ×1 + 3090 ×1, 동일 자원).**
    - A. 복제 + round-robin (회사 베이스라인)
    - B. 복제 + 속도비 가중 배정 (Router 만 똑똑한 경우. B−A = Router 의 몫)
    - C. 단계 오프로딩 (LLM: Prefill→4090 / Decode→3090, VLM: 인코더·Prefill→4090 / Decode→3090,
      DiT: Denoise→4090 / 텍스트 인코더·VAE→3090. C−B = Solver 의 몫 = 이기종 효용성의 실체)
    - D. C 의 반대 배치 (모델이 손해라고 예측한 방향. 실제로 손해면 모델의 방향성 검증)
14. **혼합 요청 실험을 추가.** round-robin 은 빈 자리가 있어도 대기시켜 유휴가 생긴다. 이기종에서
    오프로딩·분할 전략을 쓰면 단계들이 병렬로 돌아 처리량이 오르는지를 혼합(LLM·VLM·DiT) 요청으로 확인한다.
15. **1차 지표 = 처리량.** 비용 효율 등 다른 지표는 지금 정하지 않는다. 대신 분석 로그를 세밀하게
    남겨서(요청별·단계별 시각, 큐 대기, 전송, GPU 점유 등) 나중에 어떤 지표로든 다시 채점할 수 있게 한다.
16. **첫 번째 목표 = 기회 포착.** 4090·3090 에서 확인한 결과를 모델링해, PRO 6000 ×4 노드 +
    IB 로 연결된 B300 ×8 노드에서 "같은 고정 자원으로 처리량 100 → 150" 식의 기회가 있음을 보인다.
17. **이 서버는 온라인.** (폐쇄망 아님. 모델 가중치·서빙 엔진을 받을 수 있다.)

18. **scale-up 하면 결론이 달라질 수 있고, 그 달라짐을 포착하는 것도 기여다.** B300·PRO 6000 에서는
    더 큰 워크로드(모델·문맥·배치)를 쓸 것이므로 최적 배치가 4090·3090 과 다를 수 있다.
    그 달라지는 지점에서 어떻게 더 스마트하게 할지를 고려한다. (규칙이 아니라 모델을 옮긴다.)
19. **메모리 제약은 되는 만큼만.** 모델을 낮춰도 되고, 세 모달리티를 한꺼번에 안 해도 되고, 프로젝션(외삽)해도 된다.
20. **워크로드는 학술적으로 타당성이 확보되는 것으로 선정.** (선행 논문이 쓴 모델·데이터셋·트레이스 기준)
21. **DiT 는 이미지부터.**
22. **진행 방식.** 간단하고 빠르게 확인 가능한 것부터 차근차근 확인해 나간다.

    - **C·D 결과 (34/36칸, `results/hetero/ab/README.md`).** 프리필 중심: C 1.27→1.43→**1.52×**(n=200 전 구성 최고, TPOT 55 ms 대 B 87 ms),
      D 0.73~0.78×(3090 프리필 상한). 디코드 중심: C 0.13~0.25×, D 0.16~0.42× — 한 장의 KV 용량에 모든 디코드가 몰려 선점 폭주.
      혼합 n=50: D 1.16× > A > C 0.59× (디코드가 지배하면 4090 디코더가 유리) → **최적 배치 방향이 워크로드에 따라 뒤집힘** (모델 검증).
      Motivation 문장: 같은 2장·같은 200 요청에서 최선 구성이 요청 구성에 따라 바뀐다(1.52× / 1.37× / 0.13×). 고정 규칙 불가 → Solver.
    - **처리량만 보면 이 조건(8B·24GB×2·닫힌 투입)에서는 B(가중 복제)가 9칸 중 8칸 1위.** 단서: ① 2:1 은 최적 가중치가 아님(디코드 n=50 에서 1:1 에 짐),
      ② PD 도 모델을 두 장에 다 올리므로 메모리는 B 와 같음 — 차이는 디코드 KV 가 한 장에 몰리는 것, ③ 같은 처리량에서 TPOT 는 C 가 낮음(SLO 축),
      ④ 닫힌 투입은 복제에 유리. "가중치" 용어 주의: 라우팅 가중치(2:1) ≠ 모델 가중치(16GB).
    - **layer-wise 전송 확인.** NixlConnector(pull) 는 요청 단위 비동기 전송, `save_kv_layer`/`wait_for_layer_load` 는 빈 함수(layer-wise 없음).
      있는 옵션 = `enable_cross_layers_blocks`(32 레이어 블록을 연속 텐서로 묶음, 기본 off). layer-wise 는 LMCacheConnector 경로에만 있음.
      → 2026-09-23 14:40 사용자 결정: cross-layers 를 켜고 C·D 전부 재실행. 기존 결과는 `C_v1`/`D_v1` 로 보관, 혼합비 5단계(0/25/50/75/100%)로 확장.
      **주의: vLLM 0.28.0 기본 V2 모델 러너(`v1/worker/gpu/`)는 이 옵션을 무시한다**(`kv_connector.py`: "TODO: support cross_layers_kv_cache").
      설정은 파싱되지만 NIXL 호환성 해시가 off 와 동일(`a428f594…`) = 비활성. 구 러너(`VLLM_USE_V2_MODEL_RUNNER=0`)에만 구현.
      → 구 러너로 off/on 프로브 비교 후 결정 (`results/hetero/pd_xfer/v1runner_*`). 러너가 바뀌면 A·B 도 같은 러너로 재실행해야 공정.
      **결론 (15:05, 사용자 위임으로 판단):** 구 러너에서 cross on 은 켜짐(해시 `ce985a45`, 블록 2 MB), 전송 117→103 ms(−12%).
      그러나 구 러너의 프리필이 27% 느려(10,099→7,373 tok/s) C 처리량이 v1 대비 −32%(프리필 n=50) — 순손실. 전송은 병목이 아님.
      vLLM 0.29/0.30 의 V2 러너에도 cross-layer 코드 없음(RFC #42082 진행 중) → **버전 문제, 지금 해결 불가.** 재실행 중단.

    - **혼합비 스윕 완료 (15:44, `figs/fig3_mix_sweep.png`, README 표).** B 는 0~100% 전 구간 평평하게 최상위. C 는 75% 까지 최하위권,
      100% 에서만 B 와 동률/역전 → **PD 작동 구간 = 거의 순수 프리필**. D 는 25~75% 에서 C 를 2~3× 앞섬(방향 뒤집힘). 혼합 구간에서
      어느 PD 도 B 를 못 이김. 그림 4장(`figs/`) + 표 + 해석이 Motivation 재료로 준비됨. 감시자 버그(자기 체인 종료) 수정 → `watchdog.sh`.

## 참고 (이전 세션 합의, 재확정 전)

- 비용 지표: 학계 관행의 전력 포함 비용 메트릭(Splitwise 계열)을 써서 **Goodput = SAR / C** (C = 전력 포함 비용).

- DiT 단계별 실측 (이전 세션, `research-flow.md` §5④. Wan2.1-T2V-1.3B · B300 · 스텝 20):
  T5 = 시간 ~0% / 가중치 10.58 GiB 상주, DiT 루프 = 시간 72~92% / 3.3~11.1 GiB,
  VAE = 시간 8~28% / **6.0~49.0 GiB** (DiT 의 1.8~7.3배, 픽셀 수에 비례·프레임 수와 무관).
  해상도를 올리면 VAE 시간 비중은 줄고 메모리 지배력은 커진다.
  → B300(268 GiB)에서는 메모리가 남았지만 **24GB 카드에서는 용량이 결정변수**다.
  DiT 의 단계 오프로딩은 "돌아가느냐 마느냐" 를 가르는 레버 (LLM-Pilot 의 메모리 벽 동기와 같은 구조).
  비디오 기준 수치이므로 이미지 모델에서 다시 잰다.
- DiT 세 단계는 시간상 모두 연산에 묶이고(Denoise = Prefill 의 N회 반복, KV 없음), 메모리 **용량** 축에서 갈린다.
  LLM·VLM 레버는 연산 대 대역폭, DiT 레버는 연산 대 용량을 이용한다. (개념 정리, 실측 확인 전)

## B300 세션 문서와의 차이 (2026-09-22 pull 후 발견, 해소 필요)

B300 서버 세션이 같은 날(09-21) `formulation.md` · `hetsim-report.md` · `simulator-design.md` 와 `hetsim/` (S1~S3 게이트 통과)을
푸시했다. `formulation.md` 는 "이 문서와 어긋나는 서술은 이 문서가 우선" 이라 적혀 있으나, 여기 확정 사항과 어긋나는 점이 있다.

| 항목 | B300 문서 (`formulation.md` §0) | 여기 확정 | 상태 |
|---|---|---|---|
| DiT 단계 분리 (T5→Denoise→VAE) | **사장.** DiT 는 통째 워커, 레버는 카드 종류·장수만 | 확정 13-C: Denoise→4090 / T5·VAE→3090. 참고: 24GB 에서는 용량이 결정변수 | **충돌** |
| 단계 오프로딩의 범위 | EPD 는 VLM 전용 | LLM·VLM·DiT 공통 레버 | 충돌 (위와 같은 뿌리) |
| Solver/Router 역할 | solver 가 전략·비용효율·배정 규칙까지, router 는 실행만 | 확정 9: router 역할을 배치로만 제한하지 않음 | 부분 충돌 |
| 목적함수 | 집계 goodput(작업가중) 최대, 테넌트 희생 허용 | 확정 15: 1차 지표 = 처리량, 나머지는 로그 남기고 나중에 | 대체로 호환 |
| 비용 | c_k = 상각 + 전력, CE = goodput / Σ c_k | 참고: Goodput = SAR / C (전력 포함) | 호환 |
| 입력 단위 | 창별 도착률 λ_{c,w} + 밀리초 라우팅 | 확정 1·11: 개별 요청, 맞는 인스턴스 없으면 기동 비용 넣고 새로 띄움 | 호환 (같은 구조) |
| 실험 순서 | S1~S6 시뮬 먼저(GPU 불필요), S7 에서 이종 실측 | 확정 10: 실측 → 모델링 → scale-up | 순서만 다름. S1~S3 는 이미 통과, S7 실측은 이 서버에서 지금 가능 |
| AO · KV 스트리밍 | 배제 | 확정 7 | 일치 |

`simulator-design.md` 끝부분(§6 아래)에 대화 텍스트로 보이는 문단(SAR/GPU-시간과 SAR/c_k)이 붙어 있다. 정리 대상.

- **DisagFusion** (arXiv 2605.25550, 2026-05-25; refs 에 pdf·txt 추가 2026-09-22). `design.md` 가 인용만 하고 파일은 없었음.
  동기가 우리와 같음: 24GB 소비자 GPU 에 모델이 안 들어감(Wan2.1-14B 37.8GB), 인코더·디코더는 산술 강도 낮아 소비자 GPU,
  DiT 는 연산 바운드라 전문 GPU → 단계를 **이기종 GPU 에 분산 서빙**. 기여 = 비동기 파이프라인(연산·전송 겹침) +
  탄력 스케줄링(부하 변화 시 단계별 인스턴스 비율 조정, 런타임 피드백). 테스트베드 8×A10 / 8×4090 / 8×H100, 100Gbps RDMA.
  모놀리식(가중치 온디맨드 로딩) 대비 처리량 3.4~20.5×. solver·ILP·비용모델·SLO 없음, DiT 전용.
  → DiT 단계 레버의 **가장 가까운 선행 연구**. 우리 차별점: ① LLM·VLM·DiT 혼합 고정 풀, ② 해석 모델로 사전 예측(피드백 휴리스틱 아님),
  ③ 재구성 비용 인지. 주의: 그들의 베이스라인(온디맨드 로딩)은 이득을 부풀림 — 우리는 양자화·들어가는 모델 베이스라인도 포함.

- **KV offloading 용어 정리 (2026-09-22).** 세 가지를 구분한다.
  ① 스트리밍형 = LLM-Pilot 의 KVO(매 스텝 α 비율을 호스트에서 읽음). 8B·24GB 에서는 손해(이전 세션 실측, PCIe:HBM 40배).
  ② 파킹형 swap = 선점된 요청 **자기** KV 를 호스트에 내보냈다 재개 시 되읽기(재계산 회피, 부하 의존, +15%).
  ③ reuse = prefix caching / LMCache: **다른** 요청과 공유하는 프리픽스 KV 재사용(프리필 회피, 워크로드 의존).
  EpiCache 류 압축(손실형)은 범위 밖. 이전 세션의 "KV 파킹" = ②+③.
  어느 형태가 어느 상황에서 효용이 있는지는 **미결** — vLLM 이기종 실증을 진행하면서 필요할 때 다시 꺼낸다.

- **비용 = 상각 + 전력 (Splitwise 계열)** 을 같이 생각해야 함 (2026-09-22). 실측을 먼저 해 두고 논의.
  B300 문서 `formulation.md` §1 에 c_k = MSRP/(수명×8760) + TDP×이용률×전기요금 초안 있음.

  그 "노이즈" 가 곧 연구 대상. 제안: 두 층 — ① 계수 추출(β)은 스케줄러를 고정한 통제 하네스,
  ② 이득 실험(A~D) 의 ground truth 는 vLLM 그대로(회사 베이스라인과 동일). 지연 예측은 요청 단위가 아니라
  이터레이션 단위로 하고(hetsim S2: 디코드 스텝 MAPE 2.3%), 무릎 근처 꼬리는 셀이 아니라 곡선으로 보고. 판단 대기.
