**현재 주장 문장**

> 고정 온프레미스 이종 GPU 풀에서, 테넌트(LLM·VLM·DiT)가 섞여 들어올 때,
> 기존 서빙 기법을 레버로 삼아 **레버 상호작용을 모델링**하고, solver가 구성을 고른다.
> 메커니즘은 하나도 새로 만들지 않는다 (LLM-Pilot이 FlexGen을 안 만들었듯이).
> 비용은 상각 + 전력. 목적은 `max 수용 s.t. 테넌트별 SLO`.

**산출물 셋이 한 코드베이스에서 나온다.** 논문(모델 + solver + 시뮬 외삽) / 특허(오프라인 구성과 온라인 라우팅이
모델을 공유하는 방법) / 회사 납품(모델 기반 router, 베이스라인 = 현업 라운드로빈).

## 2. 확정된 사실

### 레버별 판정

| 레버 | 판정 | 숫자 |
|---|---|---|
| **PD 분리** | ✅ 확보 | 과부하 10 req/s에서 colo 0.54 vs pd 1:3 **0.79**. P:D 최적이 부하에 따라 이동 |
| **KVO 파킹** (swap·프리픽스) | ✅ 확보 | 무릎에서 goodput **+15%**, 재계산 토큰 72k → 16k |
| **KVO 스트리밍** (FlexGen식) | ❌ 기각 | 모델이 GPU에 들어가면 손해. 오프라인 처리량 3,111 → 889 tok/s |
| **VLM** | ✅ 표현됨 | 이미지 토큰 576 + 인코더 고정비. 1장 1 req/s, 2장 2 req/s |
| **AO** | 범위 밖 | 뺐음 |
| **동거 (SM 공유)** | 🟡 쟀음, 의미가 바뀜 | 보완 없음(이종 1.05× = 동종 1.02~1.06×). 페널티도 없어 **패킹 레버**. 몫 75/31 |
| **이종 카드 속도비** | ⬜ 미측정 | 데스크탑 대기 |

### 왜 스트리밍 KVO가 지나

8B 가중치 16 GB가 4090 24 GB에 들어간다 → 오프로딩할 게 KV뿐 → AO 없이는 스텝마다 다시 읽음 →
PCIe 25 GB/s 대 HBM 1,008 GB/s, **40배**. 배치 2배로 얻는 1.6배를 못 이긴다.
FlexGen이 이기는 건 **가중치가 안 들어가 스텝이 이미 느릴 때**(70B: 5.6 s/스텝)이고, 그때 호스트 KV 추가분이
상대적으로 싸다. → **KVO는 "모델이 안 들어갈 때 돌아가게 하는" 레버**. 32B~70B 프로파일이 있어야 뒤쪽 절반을 본다.

### 하드웨어·통신 (2026-09-14 실측)

```
B300 노드   vanta-gpu-worker-study01      10.201.4.151   B300 ×8       IB 800 Gbps ×8
PRO6000노드 vanta-dev-gpu-worker-infer01  10.201.4.101   PRO 6000 ×4   IB 없음
```

- 양방향 ping 0.08~0.12 ms. 링크는 100 Gbps인데 **실측 23.5 Gbps(2.94 GB/s)가 상한**.
  iperf3 8스트림과 nc가 같은 값을 내고 재전송 0 → 도구 한계가 아니라 경로의 25 GbE 구간이나 셰이퍼.
- **이종 노드 간 IB 계획 없음 (확인).** IB는 B300 쌍 안에서만.
- 그래서: 노드 간 PD는 B300 쌍에서만, **DiT 단계 분리·VLM 인코더 분리·라우팅이 이종 노드를 건널 수 있는 유일한 레버**.

### solver가 필요한 이유 (§15.11, 2026-09-14) ★

시간축 실험. 창 300초 × 60개, 재구성 33초, 최약 테넌트 SAR.

| 트레이스 | 정적 최선 | 매번 전환 | 비용 인지 |
|---|---|---|---|
| 피크 어긋남 | 0.664 | 0.986 | **0.986** |
| 같이 움직임 | 0.473 | 0.235 | **0.471** |
| 랜덤워크 | 0.262 | 0.285 | **0.391** |
| 스파이크 | 0.779 | 0.722 | **0.779** |

**"매번 최적으로 갈아타기"가 4개 중 3개에서 정적보다 나쁘다.** 비용 인지는 한 번도 안 진다.
→ 언제 *안* 바꿀지를 알아야 하고 그건 계산해야 안다. 이것이 solver의 존재 이유.
단, 이득은 테넌트 피크가 어긋날 때만(+32%p). 같이 움직이면 0.

### 층위

```
Monitor → Solver (구성, 창 단위) → Router (배정, 밀리초)
둘이 같은 성능 모델을 공유한다  ← 특허 청구항의 살
```

router 혼자로는 나쁜 구성을 못 고치고(고정 2:1:1이 0.215~0.500), solver 혼자로는 요청 배정을 못 한다.

### co-solver 현황

GPU 4장을 DiT:LLM:VLM으로 나누는 표. 수요 조합 84칸 중 실현 가능:

| | 적응 분할 | 고정 분할 최선 |
|---|---|---|
| VLM 0 req/s | 19/28 | 16/28 |
| VLM 1 | 13/28 | 8/28 |
| VLM 2 | 8/28 | 4/28 |

## 3. 정직한 약점 (새 세션에서 먼저 알아야 할 것)

1. **정적 co-solver는 얇다** — 시간축(§15.11)이 그걸 메웠다. 이제 논증은 "표를 읽으면 된다"가 아니라
   "반응형으로도 안 되고 비용을 계산해야 한다"이다. 남은 얇음은 **이종 카드**가 없다는 것.
2. **가정값 넷.** DiT의 4090 시간(B300 × 10 추정), VLM 인코더 25 ms, VLM 백본 대리, 시드 1개·합성 트레이스.
3. **PD 경로는 상류도 검증 안 했다.** colo만 vLLM 실측 대비 1%. PD 실측 검증점이 필요.
4. **격자가 거칠다.** 1·2·3·4·6·8 req/s라 파킹이 넓히는 10~15% 구간에 걸리는 셀이 거의 없다.
5. **B300 편향.** 대역폭 8 TB/s는 극단적으로 풍부해 동거 결과가 4090(1 TB/s)에서 달라질 수 있다.
6. **router 층 미구현.** 지금 있는 것은 solver 층과 재료뿐.

### C. 이종 + IB가 동시에 필요한 실험 → MIG 캡

성능이 다른 GPU 사이의 **노드 간 PD**가 유일하게 그런 경우. 이종 쌍에 IB가 없으니 B300 쌍에서 한쪽을 MIG로 자른다.

- **클럭 고정(`-lgc`)·전력 제한(`-pl`)은 쓰면 안 된다.** 연산만 낮추고 대역폭·용량은 그대로라
  연산:대역폭:용량 비가 깨진다(디코드가 비현실적으로 빨라짐). 프리필/디코드 배치가 이 비로 갈리므로 답이 뒤집힌다.
- **MIG는 셋을 함께 줄여 비가 유지**되고, 우리가 이미 오차 2%로 모델링해뒀다.
- 논문 표기: "동일 노드·동일 스택에서 연산비만 바꾼 통제 실험". 절대 숫자는 데스크탑에서.
- → MIG 자산이 헤드라인에서 내려온 대신 **이종 실험 도구**로 살아난다.
