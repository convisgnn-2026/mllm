# hetsim 진행 보고 — 2026-09-21

> 무엇을, 왜, 어떤 계획으로 만들었고, 지금 어디까지 왔는지를 한 문서에 담는다.
> 수식은 `formulation.md`, 설계는 `simulator-design.md`, 코드는 `hetsim/`, 게이트는 `hetsim/gates/`.

---

## 1. 무엇을 하려는가

사내 온프레미스 AI 서빙 플랫폼은 router 가 LLM·VLM·DiT 요청을 라운드로빈으로 GPU 에 배정한다.
우리는 그 밑에 **수학적 solver** 를 두어, 고정된 이종 GPU 풀에서 테넌트별 SLO 를 지키며
전체 goodput 을 최대화하는 구성을 고르고 router 가 그 규칙대로 배정하게 만든다.
이것을 LLM-Pilot(CCGrid'26, 1저자)의 **멀티모달·온프레미스 확장**으로 논문화한다.

**LLM-Pilot 에서 물려받는 것.** 해석적 성능 모델(회귀 보정 β) → 실행가능성 필터 → 후보 열거 → 목적 최대.
메커니즘은 새로 만들지 않고 남의 기법(PD 분리, KV 파킹, EPD, 동거)을 **레버**로 삼아 상호작용만 모델링한다.

**달라지는 것.**

| 축 | LLM-Pilot | 지금 |
|---|---|---|
| 자원 | 클라우드, 살 수 있음 | 온프레미스, 고정 |
| 비용 | 시간당 $ | 상각(MSRP/수명) + 전력(P×PUE×요금) |
| 목적 | CE = Θ/C | 작업가중 goodput 최대 (테넌트 희생 허용) |
| 워크로드 | LLM | LLM + VLM + DiT |
| 시간축 | 1회 결정 | 창 단위 재구성(33 s 비용) + 밀리초 라우팅 |

## 2. 왜 이렇게 하는가

- **정적 표로는 부족하다.** 수요가 움직이면 최적 분할이 바뀐다(4 GPU, 300 s 창 60개에서 4~30회).
- **반응형 자동화로도 부족하다.** 매 창 최적으로 갈아타면 재구성 33 s 때문에 4개 트레이스 중 3개에서 정적 고정보다 나쁘다.
  재구성 비용을 계산하는 정책만 한 번도 지지 않는다. → **언제 *안* 바꿀지를 계산해야 하고, 그것이 solver 의 존재 이유.**
- **목적함수가 배치를 뒤집는다.** 같은 하드웨어·수요에서 집계 최대화면 DiT 0장(0:4:0), 테넌트 SLA 면 1:2:1.
  운영자가 목적을 선언하고 solver 가 배치로 번역한다.
- **이전 코드(`solver/cosolve.py`)가 무너진 이유.** 시뮬레이터 둘(DiT `sim.py` + LLMServingSim)을 CSV 표로 접착해서,
  레버·카드·동거·시간 축이 늘 때마다 표 칸이 곱으로 늘고 router 를 표현할 수 없었다. 성능 모델이 코드 밖(CSV)에 있어
  논문 기여인 "모델"이 산출물에 없었다.

## 3. 전체 계획

```
Solver: σ=(카드 배정 x, 배정 규칙 r) 열거 → 메모리·링크 필터 → hetsim 으로 채점 → 비용 인지 전환   [S5·S6]
   │
hetsim: Router ──▶ Group(테넌트·레버별 인스턴스) ──▶ Card                                          [S1~S4, S7]
        단일 이산사건 클러스터 시뮬레이터. 모델은 코드 안에. 4 GPU × 300 s 창을 100 ms 안에.
```

| 단계 | 만드는 것 | 통과 게이트 | 상태 |
|---|---|---|---|
| S1 | 이벤트 루프 · Group · Router · 채점 · DiT 모델 | B300 실측 39구성 재현, legacy `sim.py` 완전 일치 | **PASS** |
| S2 | LLM 연속 배칭 엔진 · 4090 β 적합 | LLMServingSim colo 1~4장 × 6 부하 SAR 5%p | **PASS** |
| S3 | PD 분리 · 링크 · KV 파킹 | sweep1 PD 15칸 + 파킹 24칸 | **PASS** |
| S4 | VLM(E→P→D) · 동거 몫 | `pool_vlm*` 재현, 동거 합산 1.05× | 다음 |
| S5 | solver 정수 분할 | `cosolve.py` 84칸 표 일치 | |
| S6 | 시간축 전환(비용 인지) | `dynamic.py` 정책 순위 재현 | |
| S7 | 이종 카드(4090·3090) | 데스크탑 실측 β | GPU 필요 |
| S8 | router 골격 분리 | 회사 배포 인터페이스 | |

**2026-09-21 확정 결정.** 이종 노드 간 IB 는 없다(동기종만). 이종 실험은 **4090+3090 한 서버**에서 프로파일 → solver 가 scale-up →
시뮬 외삽. DiT 단계 분리(T5→DiT→VAE)는 사장, **EPD 는 VLM 전용**. 목적은 **집계 goodput(작업가중)**, 테넌트 희생 허용.
**solver 가 전략·비용효율·배정 규칙까지 결정**하고 router 는 실행한다. 기존 코드는 게이트 기준값으로만 쓴다.

## 4. 구현물 (`hetsim/`)

```
spec.py        CardType · Card · Request
core.py        Simulator(이벤트 루프) · Group(공유 큐 + 인스턴스, 규율/선택기/HOL) · Router · Link · SlotInstance
engine_llm.py  BatchInstance: vLLM 식 연속 배칭 — chunked prefill(2048), 블록 KV(16), 도달길이 예약, 꼬리 선점,
               프리픽스 복구(LRU 축출), 파킹(HostTier), 역할 colo/prefill/decode, P→D 인계, 링크 전송 가산
model/dit.py   t = t_full × (148(1−b)/S + b), 카드별 t_full 로 확장
model/llm.py   LLM-Pilot 형 스텝 시간: β0, β_w, β_kv, β_c, β_seq, β_pre, β_mix (카드별 적합)
builders.py    llm_colo(n) · llm_pd(P, D) · pd_rule
workload.py    감마 도착 + 클래스 믹스(bench/workload.py 와 같은 난수 순서) · LLMServingSim jsonl 로더
score.py       SAR · p95 · 용량 · goodput(요청/작업 가중) · 복합 SLO(callable)
gates/         s1_dit · s2_llm · s3_pd_park
```

실행: `~/venv/jinwoo/bin/python -m hetsim.gates.s1_dit` (s2_llm, s3_pd_park 동일). GPU 불필요, 각 1분 이내.

## 5. 결과

### 게이트

| 단계 | 비교 대상 | SAR 오차 평균 | 최대 |
|---|---|---|---|
| S1 DiT | B300 실측 39구성 | makespan 1.6% · 용량 2.1% · p95 7.6% | legacy `sim.py` 와 차이 0 |
| S2 LLM colo | 24칸 | 0.9%p | 8.0%p (무릎 셀) |
| S3 PD | 1:3 / 2:2 / 3:1 × 2~10 req/s, 16칸 | 1.6%p | 4.7%p |
| S3 파킹 | colo 1~4장 × 6 부하, 24칸 | 1.5%p | 16.3%p (무릎 셀 1개) |

TTFT p90 · TPOT p90 · makespan · 선점 횟수 · 재계산 토큰(오라클 99.7k 대 100.8k)까지 나란히 간다.
속도: 4 GPU 600건 DiT 3 ms, LLM 300건 0.3~0.5 s.

**무릎 셀 주의.** 부하가 용량 경계에 걸린 셀은 두 시뮬레이터가 요청의 1/3 을 다른 인스턴스로 보내고 백로그가 카오스처럼 갈라진다.
오라클 자신도 그 셀에서 파킹 on/off 로 SAR 이 0.17 움직인다. 게이트는 무릎 셀 허용폭 20%p, 그 외 10%p, 평균 5%p.

### 모델에 들어간 사실 (S2·S3에서 배운 것)

1. **스텝 시간은 두 영역.** 디코드가 섞인 스텝(CUDA graph) `16.4 ms + 34.8 µs·B + 0.211 µs·K + 85.7 µs·P`,
   순수 프리필 스텝(eager) `12.3 ms + 76.9 µs·P`. 가중치 읽기 15.9 ms 가 디코드 스텝에서는 드러나고 프리필에서는 연산 밑에 숨는다.
   (디코드 전용 79,826 스텝 MAPE 2.3%, 순수 프리필 1,063 스텝 MAPE 10.2%)
2. **선점된 요청은 캐시를 거의 못 건진다.** vLLM 은 재입장 때 도달 길이(프롬프트+생성) 블록 전부를 요구하고, 기다리는 동안
   남의 디코드가 캐시를 꼬리부터 먹는다. 복구율 평균 41%, 45% 는 0. 이 동역학을 넣어야 PD 디코드의 TPOT 꼬리가 맞는다.
3. **PD 의 비용은 링크가 아니라 디코드 풀.** 24 GB 카드에서 8B 는 KV 41k 토큰뿐이라 3:1 이면 디코드 1장이 선점 폭주.
   전송(16 GB/s)은 TTFT 에 10 ms 대만 더한다.
4. **파킹**은 쫓겨난 블록을 호스트(50 GB/s)에 두고 되읽기만 낸다. 무릎 근처에서 SAR +0.05~0.17.

### 이전 세션이 남긴 사실 (변함 없음)

PD 분리 확보(과부하 10 req/s 에서 SAR 0.54→0.79), KV 파킹 확보(+15% goodput), KV 스트리밍 기각(모델이 GPU 에 들어가면 손해),
동거는 "보완 없음 + 패킹 공짜"(합산 1.05×, 몫 75/31), 시간축에서 비용 인지 전환이 한 번도 안 짐.

## 6. 남은 구멍

- 이종 카드 미측정(3090 프로파일, DiT 4090 시간은 B300×10 추정). 데스크탑 대기.
- VLM 인코더 25 ms 가정, VLM 백본 8B 대리. S4 에서 우선 가정값으로.
- 시드 1개·합성 트레이스. 상용 트레이스 필요.
- router 층 미구현(S8). 비용·전력 목적 미실행.
- 무릎 셀 카오스: 셀 단위가 아니라 곡선·평균으로 보고해야 한다.
