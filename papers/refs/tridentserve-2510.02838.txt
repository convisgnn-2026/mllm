TridentServe: A Stage-level Serving System for
Diffusion Pipelines
Yifei Xia, Fangcheng Fu, Hao Yuan, Hanke Zhang, Xupeng Miao, Yijun Liu, Suhan Ling, Jie Jiang, Bin Cui
The Hetu Team @ Peking University
Abstract
Diffusion pipelines, renowned for their powerful visual gen-
eration capabilities, have seen widespread adoption in gener-
ative vision tasks (e.g., text-to-image/video). These pipelines
typically follow anencode–diffuse–decodethree-stage archi-
tecture. Current serving systems deploy diffusion pipelines
within astatic, manual, and pipeline-level paradigm, allocat-
ing the same resources to every request and stage. However,
through an in-depth analysis, we find that such a paradigm
is inefficient due to the discrepancy in resource needs across
the three stages of each request, as well as across different
requests. Following the analysis, we propose thedynamic
stage-level serving paradigmand developTridentServe, a
brand new diffusion serving system.TridentServeauto-
matically, dynamically derives the placement plan (i.e., how
each stage resides) for pipeline deployment and the dispatch
plan (i.e., how the requests are routed) for request processing,
co-optimizing the resource allocation for both model and
requests. Extensive experiments show thatTridentServe
consistently improves SLO attainment and reduces aver-
age/P95 latencies by up to 2.5×and 3.6×/4.1×over existing
works across a variety of workloads.
1 Introduction
Background. In recent years,Generative Vision Tasks[ 15, 19,
26, 61, 62] (GVTs), such as text-to-image [11, 28, 29, 48] and
text-to-video [27, 71, 74], have surged in popularity, prompt-

to address them. Among these,Diffusion Pipelines[ 19, 61]
have come to dominate the field for their powerful genera-
tive capabilities, giving rise to widely known pipelines such
as Stable Diffusion [11, 53] and Sora [34].

The Current Landscape. Currently, predominant prac-
tices [12, 66] ofDiffusion Pipelineserving follow two designs:
•Static, manual resource allocation for stage models. Cur-
rent systems manually allocate resources for the stage
models under a static paradigm: they either co-locate
all stages on each GPU (for small pipelines) or stati-
cally deploy the pipeline in a disaggregated fashion
and assign a fixed number of replicas to different stages
(for large pipelines).
•Static, pipeline-level resource allocation for requests. When
handling different requests, current systems assign a
fixed number of GPUs to every request (a.k.a., use the
same parallelism [24, 33, 37, 58] strategy). Meanwhile,
for any single request, the different stages also share
the same amount of allocated GPU resources at the
pipeline-level.
However, after our detailed analysis of the architecture
and workloads ofDiffusion Pipelines(§3), we find that such
a naïve, static design is inefficient for the following reasons:
First,Diffusion Pipelinesare bothstage-heterogeneousand
request-heterogeneous, rendering this naive resource alloca-
tion inefficient and wasteful. On the one hand, GVTs exhibit
substantial workload variation across requests due to dif-
ferences in target resolutions or video durations, and dif-
ferent requests manifest distinct scalability characteristics
(§3). Hence, statically allocating identical resources to all
requests is inefficient, as illustrated in Figure 2(a). On the
other hand, stages within the sameDiffusion Pipelinehave
distinct architectures and behaviors, and therefore exhibit
different scalability (§3). Thus, when processing one request,

Second, production GVT workloads exhibit complex and
highly dynamic arrival patterns [2, 57]. Particularly, in §3, we
analyze that as workload arrival patterns shift, the resources
required by different stages also change, thereby render-
ing static deployments maladaptive. Besides, the change in
workload arrival patterns also necessitates adjusting the par-
allelism choices of different requests. Unfortunately, current
approaches fail to handle such dynamicity.
Therefore, to serve diffusion pipelines efficiently, we ex-
pect a system capable of fine-grained, dynamic resource al-
location for both request processing and model deployment.
However, realizing such a system presents two challenges:
• How to efficiently support such fine-grained, dynamic
processing and deployment?All existing diffusion serv-
ing systems, such as xDiT [12] and VideoSys [66], are
coarse-grained and pipeline-level. Once varying re-
sources are allocated to different requests and stage
models, how to carry out the serving process efficiently
is an unexplored question.
• How to accurately solve dynamic resource allocation?
For resource allocation and processing of each request,
the inter-stage topology and communication, tight
GPU-memory budgets [40–42], and divergent resource
demands together vastly expand the decision space.
Meanwhile, for resource allocation of stage models,
differing requirements across pipelines and dynam-
ically shifting workload arrival patterns [ 2, 57] also
exacerbate the complexity of solving the problem.
Our Solution. To address this, we proposeTridentServe,
the first system that supports dynamic, stage-level resource
allocation for both request processing and model deploy-
ment. To facilitate stage-level processing and deployment,
TridentServeintroduces two abstractions: it casts model-
side allocation asplacement plans, enabling automatic, dy-
namic deployment; and casts request-side resource allocation
asdispatch plans, enabling dynamic, stage-level resource al-
location (Figure 2 (c)) for request processing. TheRuntime
EngineofTridentServeis in charge of the efficient execu-
tion of both plans. For theplacement plan, it automatically
deploys the pipeline at initialization and performs anAdjust-
on-Dispatchmechanism that integrates stage-model resource
transitions into request processing, allowing the system to
flexibly adapt to diverse workload patterns while achieving
seamless, no-downtime deployment switch. For thedispatch
plan, we define an atomic three-step procedure to execute
requests at the stage-level efficiently.
As for plan generation, we 1) employ aDynamic Orches-
tratorforplacement plangeneration, which automatically
optimizes model deployment given the model and workload
statistics without manual tuning; and 2) propose a two-step
Resource-A ware Dispatcherto generatedispatch plans, which
achieves efficient resource utilization while greatly improv-
ing overall system efficiency.
We summarize our main contributions as follows:
• We present the first systematic, stage-aware analy-
sis of diffusion pipelines, revealing the asymmetry in
resource demand across stages and requests, which
motivates astage-levelserving paradigm.
• We developTridentServe, the firstDiffusion Pipeline
serving system withdynamic, stage-levelresource al-
location for both models and requests. It integrates a
Dynamic Orchestratorand aResource-A ware Dispatcher
that co-optimize the model placement and request dis-
patching, markedly improving serving efficiency and
robustness under complex workload arrival patterns.
• TridentServeauto-deploys pipelines to eliminate la-
borious manual tuning. Extensive experiments show
that it consistently improves SLO attainment, aver-
age/P95 latencies by up to 2.5×, and 3.6×/4.1× against
the strongest baseline under a variety of workloads.

Based on the above analysis, we distill two design princi-
ples for efficientDiffusion Pipelineserving.
Principle 1: Stage-level Dynamic Resource Alloca-
tion for Requests.Because scalability varies both across
requests and across the stages within a single request, re-
source needs differ at the stage-level. Accordingly, allocation
should be dynamic andstage-levelfor each request, rather
than static andpipeline-level.
Principle 2: Dynamic Resource Allocation for Stage
Models.In real-world scenarios, workload arrival patterns
fluctuate over time, and the resource demands of individual
stages shift accordingly. Moreover, different pipelines have
distinct architectures (Table 2), leading to heterogeneous de-
ployment needs. Therefore, the system should automatically
deploy and dynamically allocate resources to stage models,
adapting to pipeline specifics and workload dynamics rather
than relying on brittle, static manual configurations.
Our Design.Motivated by these, we design a unified
serving system,TridentServe, that supportsStage-level,
dynamic resource allocationfor both requests (§6.2) and stage
models (§6.1), which is all backed by aRuntime Engine(§5).

5.1 Profiler and Monitor
Profiler.Leveraging the strong predictability [ 21, 47] of
execution time and memory footprint in GVT workloads,
TridentServeprovides a comprehensive offline profiler. On
pre-supplied data, the profiler collects information at two
levels of granularity:
• Request Metadata.For each stage of a range of re-
quests, it measures the expected running time and
peak activation memory under each parallel strategy.
• Request Statistics.Statistical information includes
the processing length and peak memory distribution of
all stages, which will be used to guide theOrchestrator
andDispatcherin generating plans (§ 6).
Monitor.Monitorruns in a periodic, clock-driven behav-
ior, observes the GPU worker cluster information to furnish
real-time planning feedback along two dimensions:
• GPU-worker Status.For each GPU 𝑔, theMonitor
reports whether it is idle, its current placement 𝜋𝑔,
and residual memory capacity. If the worker is busy, it
also reports the dispatch plan in execution, the start
timestamp, and the estimated runtime.
• Stage Throughput.TheMonitorrecords the process-
ing rate for each placement type,𝑣𝜋, enabling theOr-
chestratorto rebalance placements when throughput
becomes skewed.
5.2 Execution ofDispatch Plan
TheResource-A ware Dispatchertriggers in a clock-driven
manner and generates thedispatch plansto theRuntime
Enginefor execution. For eachdispatch plan, once its re-
quired GPU set is idle and the predecessor stage’s plan has
completed, theRuntime Enginereserves the resources and
executes it in three steps:Dynamic Reinstance,Stage Prepare,
andMerging Execute. Below, we first introduce the three
steps and then illustrate a concrete example in Figure 6.
Dynamic Reinstance.Given adispatch plan, theRuntime
Enginetemporarily groups the targeted GPU workers into
an execution instance and activates the requisite commu-
nication group. To avoid per-dispatch setup overhead and
the excessive buffer footprint that would result from pre-
initializing a communication group for every parallel strat-
egy [49], we prepare only a small hot set ofintra-machine
worker combinationsand reuse a single communication buffer
within each combination. Other infrequent combinations
are lazily initialized on first use. This hot-set and lazy-init
design enables millisecond-scale reconfiguration without
global pauses and keeps the memory footprint bounded, pre-
venting communication-buffer accumulation.
Stage Preparation.After forming the execution instance,
the Runtime Engine prepares (i) the resident model replica for
the target stage and (ii) the stage inputs. If theplacement plan
has recently changed such that the required stage replicas
aretemporarilynot resident on the selected workers, we
invokeAdjust-on-Dispatchat this step (see §5.3 for details).
Since dispatch is performed at the stage-level, the in-
puts for the currentdispatch planmay not reside on the
selected GPU set. To curb additional input-transfer latency,
we employ aproactive pushscheme that maximizes compute–
communication overlap without inflating device memory.
Concretely, each GPU worker maintains a device-resident
handoff buffer(HB) for temporarily staging inter-stage ten-
sors. When a preceding dispatch plan completes and a suc-
cessor exists, the preceding stage proactively enqueues its
outputs into the successor stage’s HB so the successor can
read them directly at launch; if the successor stage is still

5.3 Execution ofPlacement Plan
TridentServeappliesplacement switcheswith anAdjust-
on-Dispatchpolicy: the system updates placementmetadata
immediately, while actual replica changes are deferred to
the next dispatch that needs them. This enables seamless
transitions without downtime.
Stage Replica Management.Each node maintainsone
shared CPU replica per stage. GPU workers host only the
stages assigned by the current placement.
Adjust-on-Dispatch.TheMonitortracks per-stage through-
put over a sliding window of length𝑇win2. If the fastest stage
is at least1.5× the slowest, theDynamic Orchestratorderives
a new placement planPswitch.Runtime Engineimmediately
updatesPswitch in its placement metadata; no replicas are
actually changed yet. TheDispatchergenerates newdispatch
plansaccording toPswitch. Since every worker executes plans
in a FIFO strategy, the in-flight/queued dispatches created
under the old placement will finish as planned before the
new ones, which ensures the safety ofAdjust-on-Dispatch
and will not cause erroneous execution. When a dispatch
plan based on Pswitch finds that the required stage is not
resident on GPU,Runtime Engineloads the needed stage
replica onStage Preparationof the dispatch plan through a
two-step efficient transfer manner: 1) it first tries an intra-
node GPUDirect P2P from a peer GPU that already hosts
the stage; 2) otherwise it loads the stage replica from the
node’s pinned, shared CPU replica. Transfers use a block-
wise streaming transfer to remain OOM-safe. These actions
are asynchronous and only occur when a plan truly needs
them.

6.1 Placement Plan
Dynamic Orchestratorgenerates P following the two princi-
ples:
Principle 1: Eliminate avoidable inter-stage communica-
tion. To eliminate unnecessary inter-stage communication,
we should, whenever possible, try to execute as many stages

minimal communication per request, the global communica-

Principle 2: Balance the processing speeds of the three
stages to avoid stage congestion. To balance processing speeds
across stages, we estimate each stage’s processing rate and
allocate resources to each stage in proportion to these rates.
Guided by these principles, we later (i) further formalize
placement, (ii) derive thesingle-request solutionthat mini-

7 Implementation
The core ofTridentServecomprises about 12K lines of
Python/Triton [69] code in total: theRuntime Engineis 10K
LOC and the Planners are 2K LOC. We have integrated pop-
ular diffusion models (roughly 16K LOC in total), including
Stable-Diffusion[ 11],PixArt[ 7, 8],Flux[ 29],Cogvideo[ 74],
HunyuanVideo[ 27], andHunyuanDiT[ 31]. We also support
a dynamic batching mechanism when there are multiple
lightweight requests to be served. Besides, although our so-
lution above concentrates onSP, it is compatible withMP
by simply treating multiple devices as one. We leave more
details of dynamic batching andMPintegration in Appen-
dix E. In theRuntime Engine, we implement asynchronous
concurrent execution withray[ 36] and coroutines [56], and
useNCCL[ 43] andNIXL[ 3] as communication backends. To
implement theDispatch plansolver, we use the PuLP [ 35]
libraries for solving the ILP problem.

8.4 Ablation Study
E2E AblationWe conduct ablations onHunyuanVideoand
Fluxusing thedynamicandsteady (medium)workloads,
removing one component at a time:
•wo-switch: disable placement switch, only useP 𝑖𝑛𝑖𝑡 .
• wo-stageAware: disable stage-level resource alloca-
tion, and align all GPU demand with theDiffusestage.
• wo-scheduler: replace ourResource-A ware Dispatcher
with a simple greedy SRTF policy; each stage still uses
profiled-optimal parallelism strategy.
Results (Figure 14) show: (i)placement switchingis crucial
under dynamic load shifts, reducing latency by 33.1% and
17.6% inFluxandHunyuanVideo; under theSteadyworkload,
the gains are more modest—11.7% and 6.2% respectively. It
also improves SLO attainment by mitigating stage-rate im-
balance. (ii) on average,stage-level allocationconsistently
reduces latency by 22.3% and 25.3% and improves SLO at-
tainment by 10.0% and 24.2% inFluxandHunyuanVideo,
regardless of workload, owing to more efficient resource use;
(iii) theglobal schedulersubstantially boosts SLO attainment
up to 36.8% and 42.4% inFluxandHunyuanVideo, while also
yielding a certain reduction in latency.
Ablation forAdjust-on-Dispatch.To assess the effec-
tiveness ofAdjust-on-Dispatch, we use Flux’sDynamicwork-
load and monitor a certain request (1024p) that completes
immediately before an adjustment is required. We compare
its completion time under two scenarios—naïve downtime ad-
justment andAdjust-on-Dispatch, with the breakdown shown
in Figure 13. The results show that downtime adjustment
incurs substantial overhead because the system must shut
down for an extended interval during which no requests are
processed, whereas our approach amortizes the adjustment
by performing it concurrently between dispatches, adding
virtually no runtime.

9 Related Work
Diffusion Pipeline Serving.With the rapid rise ofDiffu-
sion Pipelines, several works target serving optimization. NIR-
VANA [1] reuses intermediate noise across requests to reduce
denoising steps; DIFFSERVE [ 2] cascades small and large
models to balance speed and quality; PATCHEDSERVE [65]
caches at the patch-level to exploit diffusion redundancy;
FlexCache [64] stores and compresses intermediate states by
leveraging step similarity for acceleration. All of the above
arelossy, algorithmic accelerations and thus orthogonal to
our approach. To the best of our knowledge, we are the first
to deliver alosslessacceleration from a systems perspective.
Disaggregated Serving.Disaggregated serving [ 50, 51,
78] targets pipelines whose stages have contrasting resource
11
profiles. In LLM inference,prefillis compute-bound while
decodeis memory-bound; co-locating them degrades TTFT
and TPOP, so systems such asMooncakeandDistServe
separate these stages [50, 78]. As multimodal inference ma-
tures, frameworks analogously isolate theencodestage from
prefill/decodeto raise throughput, e.g.,EPD[60].
10 Conclusion and Future Works
This work analyzes diffusion pipelines from both architec-
tural and workload perspectives, revealing a pronounced
imbalance in resource demands across requests and stages.
To address this, we presentTridentServe, the first system to
support dynamic, stage-level resource allocation for both re-
quest processing and model deployment, jointly optimizing
them to efficiently serve complex workloads.
As a future direction, we plan to adapt our system to
heterogeneousGPU pools, exploiting each stage’s distinct
compute–memory profile to map it to the most cost-effective
GPU tier. We also plan to extend this stage-level architecture
tomulti-modelserving. Lastly, although this work is the first
to articulate the problem of stage-level resource allocation,
our current solution relies on certain heuristics (e.g., fixed
model parallelism E.2), which we aim to refine in future
work.

Integration with Dynamic Batch.From the analysis above, we conclude that different requests and different stages each
have distinct optimal batch sizes (we define the optimal batch size as the largest batch size whose latency increase is less than

and then perform resource allocation and execution at the granularity of the request batch; the method requires virtually no
changes.
Meanwhile, because theEncodestage’s optimal batch size exceeds that of theDiffusestage, some Γ𝐸 may not reach their
optimal batch size. We proactively merge theΓ𝐸 that run exclusively on𝜋=⟨𝐸⟩ , consolidating those that have not yet reached
the optimal batch size, thereby further improving resource utilization.
E.2 Model Parallelism
Because model parallelism is far less efficient than sequence parallelism at the same degree, we enable model parallelism only
when the model parameters cannot fit on a single GPU. We enable model parallelism solely for theDiffusestage, sinceEncode
requires no parallelism and theDecodestage has very small model parameters, rendering model parallelism highly inefficient.
When theDiffusion modelcannot fit on a single GPU, we first determine the minimal model-parallel degree 𝑘𝑚𝑖𝑛 such that,
under the maximum load, the per-GPU shard of theDiffusion modelfits within one GPU’s memory. We then carry out the
placement planallocation anddispatch plansolving at the granularity of 𝑘𝑚𝑖𝑛 GPUs (rather than a single GPU), which leaves
all our methods unchanged.
